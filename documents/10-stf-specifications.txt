# Solis STF Specifications — Detailed Reference

## 1. Motion Types

Three distinct motion types, each requiring different handling:

### sys_bound (System-Bound)
- **What**: Parameter changes executed automatically by the Integrity Engine
- **Example**: Adjusting Ws decay rates, modifying domain weights, updating standing thresholds
- **Implementation**: The system executes the change directly — no human implementation needed
- **Filing**: Motion specifies the parameter change; system enforces it

### non_system (Non-System / Directive)
- **What**: Directive to named implementing Circles — requires human execution
- **Example**: "Space Law Circle shall publish a debris liability framework guide by Q3"
- **Implementation**: Named Circle(s) must execute. Filing without naming implementing Circles returns 422 error
- **Key rule**: A directive with no named responsible body is rejected at the API layer
- **Gate 2**: Interpretive — the implementing Circle interprets how to fulfil the directive

### hybrid (Both)
- **What**: Combines system-bound parameter change AND human directive
- **Example**: "Adjust domain weight for Space Law + Space Law Circle shall publish updated guidelines"
- **Implementation**: System executes the parameter change; named Circle(s) execute the directive

### Why This Taxonomy Exists
- A software system needs to know which decisions it enforces automatically vs. which require human execution
- The paper's model assumes Circles implement faithfully; this taxonomy makes the distinction explicit
- The `implementing_circle_ids` requirement operationalises accountability: "the decision-makers are also the implementers"

## 2. vSTF Assessment of Steward

### Purpose
Evaluate whether a candidate is suitable for stewardship in a specific Circle.

### Trigger
Candidate x has been fronted for stewardship in Circle y.

### Context Provided to Assessor
- **Circle y's mandate**: Associated with dominion over:
  - Knowledge domains (e.g., Space Law, Remote Sensing)
  - Experiential domains (e.g., Debris Tracking, Policy Analysis)
  - Affiliation domains/orgs (e.g., Uganda Astronomical Society)
- **Auto-match data**: Intersection of candidate's Ws|Wh vs Circle requirement
- **Assessor task**: Further investigation on candidate AND circle

### Verdict
Scale your approval of candidate as a steward of the above:

```
Disapprove [------------------------------------------] Approve
           0                                            100
```

### Output
- Approval score (0–100)
- Rationale/justification
- Filed to ledger (reviewer attribution sealed)

## 3. vSTF Assessment of Competence

### Purpose
Evaluate and adjust a member's self-declared competence claims.

### Trigger
Member x has submitted new competence claims.

### Assessor Task
1. Investigate, evaluate, and assess whether claims are acceptable
2. Adjust where you think necessary
3. Mark evaluated claims
4. Adjust the rest or leave as-is based on your judgment

### Assessment Interface
For each claimed domain:

| Domain | Claimed Wh | Adjusted Wh | Evaluated | Notes |
|--------|-----------|-------------|-----------|-------|
| Space Law | 1,200 | [slider/input] | ☑ | |
| Remote Sensing | 800 | [slider/input] | ☑ | |
| Policy | 400 | — | ☐ | Insufficient evidence |

### Evaluation Options
- **Slider**: Drag to adjust Wh value
- **Direct input**: Enter exact number
- **Leave unmarked**: With reason:
  - Insufficient evidence
  - Insufficient claims
  - Omitted while evaluating
  - Unable to effectively evaluate the specific domain
  - Any other sufficient reason

### Comments
Free-text evaluation comments at the bottom.

### Aggregation
Your evaluation will be collectively aggregated against other evaluators to derive the final competence weights.

## 4. aSTF Structured Rubric (Motion aSTF)

### Purpose
Guide reviewers toward their verdict on a motion using a four-dimension scoring instrument.

### Dimensions (30 points total)

| Dimension | Max | Measures |
|-----------|-----|----------|
| **Jurisdiction** | 9 | Does the Circle have mandate authority here? |
| **Depth/Effort** | 5 | Was deliberation substantive? |
| **Alignment/Conflict** | 10 | Does the decision advance org tenets? Undisclosed conflicts? |
| **Competence** | 6 | Were the right people in the deliberation? |
| **Total** | **30** | |

### Weighting Rationale
- **Alignment/Conflict (10)**: Heaviest — core PAAS legitimacy check. A Circle acting within mandate but advancing faction interests is more serious than thin deliberation.
- **Jurisdiction (9)**: Heavy — out-of-mandate action is structural, not correctable by more effort.
- **Depth/Effort (5)**: Lighter — can be addressed through more deliberation.
- **Competence (6)**: Lightest — composition gaps can be addressed through the Inferential Engine's gap-filling.

### Key Principle
The rubric **guides, it does not decide**. Reviewers see a running total as they score, but the verdict (Approve/Revision Request/Reject) is explicitly filed as a separate judgment. Scores are published evidence; the verdict is human determination.

**Mechanising the verdict from the score would undermine the purpose of independent human audit.**

### Malpractice Flagging
- Motion aSTF reviewers can flag specific deliberation participants for jSTF pre-referral alongside any verdict
- Even an Approve verdict can include flags — the motion can be sound while a participant's behaviour was not
- Flag creates a `jstf_pre_referral` ledger event
- The Judicial Circle decides whether to commission a full investigation

### Verdict Options
- **Approve**: Motion passes as Resolution
- **Revision Request**: Motion returned to deliberation cell with specific revision notes
- **Reject**: Motion rejected with explanation

## 5. Periodic aSTF (p-aSTF) — Circle Health Review

### Purpose
Two-layer periodic review assessing Circle health at both the collective and individual level.

### Layer 1: Circle Rubric (All Reviewers, 30 pts)

Based entirely on **publicly observable information** — the Circle profile page, Commons activity, motion and resolution record. No access to internal deliberations required.

| Dimension | Max | Measures |
|-----------|-----|----------|
| **Activity** | 6 | Is the Circle visibly active in governance? |
| **Competence Fit** | 7 | Does actual member Ws match mandate domains? |
| **Discipline** | 6 | Does it stay within its mandate? |
| **Cohesion** | 5 | Does it act as a collective or as isolated individuals? |
| **Delivery** | 6 | Does it follow through — enacted resolutions, Gate 2 pass rate? |
| **Total** | **30** | |

**Competence Fit** is pre-computed by the Inferential Engine (percentage of mandate domains with Ws ≥ 800 among Circle members) and surfaced as a data point. The reviewer translates the number into a score — the data informs but does not replace the judgment.

### Layer 2: Member Rubric (Assigned Reviewers Only, 35 pts health + 2 risk flags)

Filed only for the reviewer's **assigned members** (1–3 per reviewer). Reviewers have access to assigned members' public governance records AND their deliberation contributions within the Circle.

| Dimension | Max | Measures |
|-----------|-----|----------|
| **Effectiveness** | 5 | Responsive to matters that concern the Circle |
| **Stewardship** | 7 | Projects the org's vision in their work |
| **Participation** | 5 | Present and active |
| **Investment** | 8 | Genuine skin in the game vs. seat-filling |
| **Productivity** | 6 | Adds unique value |
| **Role Fit** | 4 | Understands what the Circle requires of them |
| **Health subtotal** | **35** | |

**Weighting rationale:**
- **Investment (8)**: Heaviest — strongest single predictor of governance quality
- **Stewardship (7)**: Second — carrying the org's vision is the central PAAS accountability principle
- **Role Fit (4)**: Lightest — role understanding can develop; not grounds for serious concern on its own

### Risk Flags (Separate from health score, not additive)

| Flag | Range | Trigger | Action |
|------|-------|---------|--------|
| **Replaceability** | 0–5 | Score > 3 | Knowledge-transfer mandate — structural risk signal, not quality judgment |
| **Indispensable** | 0–5 | Score > 3 | jSTF pre-referral consideration — the anti-capture signal |

### Bipartite Reviewer Assignment

- p-aSTF pool assembled using independence-weighted candidate scoring (same as motion aSTF)
- Each reviewer is assigned **1–3 Circle members** (never all)
- Each member receives assessments from **2–3 independent reviewers**
- Reviewer sees only their assigned members' data — not the full Circle roster, not other reviewers' scores

**Design rationale**: Limits each reviewer's exposure to Circle's internal affairs while ensuring sufficient independent coverage. Reflects PAAS principle of maximum participation: many reviewers each doing a bounded task rather than a small set doing exhaustive work.

### Health Tier

Each reviewer files one of three health tiers alongside their rubric:

| Tier | Meaning |
|------|---------|
| **Healthy** | Circle is functioning well |
| **Watch** | Minor concerns, monitor |
| **Concern** | Serious issues, action needed |

The Integrity Engine **majority-votes** the final tier. The tier is the reviewer's judgment; the rubric scores are the published evidence.

### Reviewer Availability

- Members can declare **standing availability** for review work
- Distinct from Curiosity (topical interest) — this is availability for the audit role specifically
- The Inferential Engine uses it to build review pools on demand
- Reviews happen continuously on each Circle's individual schedule (anchored to founding date, event-triggered on anomaly flags)
- **No global audit calendar** — no term-based politics

### Ledger Publication

All scores, verdicts, and health tiers are published to the open ledger after review completes:
- **Reviewer attribution is permanently sealed** — who scored whom is never disclosed
- Every org member can see aggregate scores for every Circle and every member
- **Transparency is maximal; retaliation surface is eliminated**

### Unit of Assessment

- **Individual member** is the unit of assessment
- **Aggregate** is the Circle
- A Circle with 7 members produces:
  - 7 member rubric assessments (each from 2–3 reviewers)
  - 1 circle rubric assessment (from all reviewers)
- Circle health score = aggregate of member-level + Circle-level — NOT the reverse
- A Circle with one member pulling the score down is distinguishable from uniformly mediocre Circle

**Why**: PAAS replaces positional authority with individual demonstrated competence. A Circle health score that doesn't trace to individual members makes accountability diffuse. The member-level breakdown is the substantive finding; the aggregate exists for convenience.

## 6. Deliberation Cell Structure

A deliberation cell is the core governance mechanism. Each deliberation cell uses a **layout-split** (1fr 300px sidebar).

**Main content:**
1. **Proposal Origin** — the trigger source (discussion thread, direct proposal, system-bound edit)
2. **Deliberation** — a chat thread where participants discuss the proposal
3. **Accept checkbox** — "I confirm this discussion record accurately reflects the deliberation" — must be checked to enable vote (vote happens in modal)
4. **Decision Status Bar** — quorum status, vote result, Submit Resolution or Close Debate button

**Sidebar:**
1. **Participating Circles** — active circles with member counts, ghost/scar for self-disqualified
2. **Deliberation Guide** — explanation of what a deliberation cell is and the flow
3. **Draft Resolutions** — summary cards for each resolution, Edit/View button → modal, + Add Resolution

### Resolution vs Motion

A **resolution** is the recorded outcome of deliberation — the decision that is voted on, not the original proposal. The proposal starts the discussion; participants draft one or more resolutions based on deliberation. Failed resolutions are still recorded as failed.

Resolution type is derived from content:
- **Directive** (non-system) — circle(s) implement
- **System** — auto-executed by Integrity Engine
- **Hybrid** — both

Multiple resolutions can exist in one deliberation cell. Each spawns its own aSTF.

### Resolution Drafting Modal

Full overlay modal with:
- Resolution text (editable textarea, pre-filled with proposal)
- Action field (free text with autofill presets: Community Policy, Declaration, Deliverable Document, Service Contract, Agreement, Letter/Communication) + implementing circle(s) selector
- Vote control: Yea / Nay / Abstain buttons + per-domain vote breakdown table
- Save button (nullifies all existing votes on save)
- Vote buttons enabled/disabled by accept checkbox in main view

No type selector exposed to users. Resolution type is implicit — determined by the deliberation trigger context. Circle/Settings edits → system-bound. Direct proposals → directive.

### Accept Record Checkbox

Before voting, participants must confirm the discussion record is accurate. This activates the vote buttons. Ensures deliberation record is complete before voting.

### Multi-Circle Participation

Deliberation cells can have multiple circles participating, not just the originating circle.

Circles can **self-disqualify** from a deliberation — this is an auditable decision. The circle appears as a "ghost/scar" in the participating circles list, showing "withdrew from deliberation by: [member name]" to indicate which member made the withdrawal decision. The scar is permanent and visible to auditors.

### Voting Mechanics

**Three vote options:** Abstain, Nay, Yea

**Per-member vote weight:**
Each member's vote weight = their Ws (soft competence) intersection with the deliberation domains. If a member has 2800 Ws in Xenobiology but the resolution is about Space Law and Liability, their Xenobiology Ws contribute zero influence. Their Veterinary Biology Ws (200) may be significant if the resolution touches that domain.

**Per-domain vote breakdown:**
For each domain the resolution covers, the system shows a table with:
- Domain name
- Yea Ws total (sum of all yea voters' Ws in that domain)
- Nay Ws total (sum of all nay voters' Ws in that domain)
- Total Ws in that domain
- Individual voter contributions (avatar, Ws, vote direction)

**Aggregate vote:**
The final vote is an aggregate of all stewards on all intersecting domains with the resolution, across all domains of the resolution. Shown as total Yea Ws vs total Nay Ws across all domains, with a final row summarising.

### Decision Status Bar

Below the vote table:
- Quorum status (e.g., "Quorum: 4/7")
- Vote result (e.g., "Yea 4,960 · Nay 932 (passes)")
- **Submit Resolution** button — green, active when quorum met + passes. Sends to aSTF for blind adjudication.
- **Close Debate** button — red, always active. Anyone can press to crystallise the cell. Resolution recorded as final outcome.

### System Settings Modal

Tabbed full overlay with four tabs:
1. **Circle** — name, status, description, max members
2. **STF** — min/max vSTF assessors, aSTF assessors, durations (days)
3. **Quorum** — minimum participants, minimum % of members, pass threshold, abstain limit
4. **Deliberation** — max days, auto-close inactivity, max resolutions, vote nullify on edit

Submit creates a system-bound proposal to the deliberation cell. Also accessible from Circle Home sidebar.

### Voting Mechanics

**Three vote options:** Abstain, Nay, Yea

**Per-member vote weight:**
Each member's vote weight = their Ws (soft competence) intersection with the deliberation domains. If a member has 2800 Ws in Xenobiology but the motion is about Space Law and Liability, their Xenobiology Ws contribute zero influence. Their Veterinary Biology Ws (200) may be significant if the motion touches that domain.

**Per-domain vote breakdown:**
For each domain the motion covers, the system shows a table with:
- Domain name
- Yea Ws total (sum of all yea voters' Ws in that domain)
- Nay Ws total (sum of all nay voters' Ws in that domain)
- Total Ws in that domain
- Individual voter contributions (avatar, Ws, vote direction)

**Aggregate vote:**
The final vote is an aggregate of all stewards on all intersecting domains with the motion, across all domains of the motion. Shown as total Yea Ws vs total Nay Ws across all domains, with a final row summarising.

### Vote and aSTF

When all participants have voted and the motion passes, the cell creates or opens an aSTF for blind adjudication.

### Proposal Origins

A proposal enters a deliberation cell through one of three paths:

1. **Discussion thread → steward proposal**: A user creates a discussion thread, participants discuss, and a steward creates a proposal from that thread. The proposal links back to the source discussion thread.

2. **Direct steward proposal**: A steward directly creates a proposal without a preceding discussion thread. The steward writes the proposal themselves.

3. **System-bound proposal**: A steward makes changes to a system setting or circle profile, submits the changes as a proposal. When the resolution passes, the approved system settings are activated automatically by the Integrity Engine.

## 7. jSTF — Judicial Investigation Cell

### Trigger
Any member can report any member. The report is surfaced as an **anonymous post to the Commons**, visible to stewards. Any steward can sponsor the report, which activates a jSTF.

### jSTF Deliberation
The jSTF deliberates on the report in a blind cell. During deliberation, the jSTF can:

1. **Restrict reported user activity** — e.g., suspend steward privileges, limit participation in certain cells, during the investigation period
2. **Select punitive action** if warranted — based on policy resolutions previously passed by the Commons (cited as precedent)
3. **Push a disciplinary motion** — which goes to aSTF for audit

### aSTF Audit of jSTF Disciplinary Motion
- aSTF audits the **decision**, not the members
- aSTF **never sees jSTF members** — complete separation
- aSTF reviews whether the disciplinary action is proportionate and consistent with Commons policy

### Resolution
When the disciplinary motion passes aSTF audit, the resolution can be:

1. **System-bound**: Remove from circle, trigger fresh vSTF, freeze Ws for a set time, among others
2. **Non-system disciplinary**: Applied as per policy resolutions passed before, cited as precedent

### Why Anonymous Reporting?
- Protects reporters from retaliation
- Stewards who sponsor the report take responsibility for the claim
- Balances accountability with safety
- Prevents abuse: steward sponsorship ensures someone is accountable for frivolous claims

### Activity Restriction During Investigation
- jSTF can restrict a reported member's activity during deliberation
- Examples: suspend steward privileges, limit participation in certain cells
- Restriction is temporary, applied with proportionality
- The restriction itself is a system-bound action (applied by the Integrity Engine)

### Policy Citation for Punishment
- jSTF cannot invent punishment — it must cite existing policy resolutions
- Punishment is applied as per the policy, not ad hoc
- This ensures fairness and consistency across all jSTF proceedings

## 8. Resolution Lifecycle — End-to-End

```
Discussion Thread (any member) → Steward creates Proposal → Deliberation Cell (stewards + domain members)
                                                          ↓
                                              Accept record as true
                                              Draft Resolution(s) (editable in modal)
                                              Per-domain vote table (Ws intersection)
                                              Yea Ws vs Nay Ws per domain + aggregate
                                                          ↓
                                              If passes: Submit Resolution → aSTF (blind cell)
                                              If fails: Close Debate → Failed resolution recorded
                                                          ↓
                                              aSTF verdict: Resolution / Rejection
                                              → opens xSTF → Deliverable

jSTF: Report (any member) → Anonymous post → Steward sponsors → jSTF Cell (blind)
                                                              ↓
                                                      Activity restriction (if needed)
                                                              ↓
                                                      Disciplinary resolution → aSTF audit
                                                              ↓
                                                      System-bound / Non-system resolution
```

### Resolution Lifecycle Summary

| Component | Detail |
|-----------|--------|
| Vote options | Abstain, Nay, Yea |
| Pre-vote | Accept record checkbox must be checked |
| Member weight | Ws in intersecting domains only |
| Per-domain breakdown | Table: Yea Ws / Nay Ws / Total / Voters |
| Aggregate | Sum of all Yea Ws vs Nay Ws across all domains |
| Pass condition | Aggregate Yea Ws > aggregate Nay Ws |
| Self-disqualify | Auditable withdrawal — "withdrew from deliberation by: [member name]" |
| Resolution drafting | Modal: text, type, system settings, non-system actions, implementing circles |
| Multiple resolutions | Each spawns its own aSTF |
| Edit nullifies votes | Any edit to resolution text or type nullifies existing votes |
| Submit Resolution | Green button, active when quorum met + passes → aSTF |
| Close Debate | Red button, always active → crystallises cell, resolution recorded |
| System Settings | Tabbed modal (Circle/STF/Quorum/Deliberation) → submits system-bound proposal |
| Resolution types | Directive (circles implement), System (auto-executed), Hybrid (both) |
| System-bound settings | Circle CRUD, approval, org CRUD, domain CRUD, aSTF periods, STF composition |
| Non-system actions | Policy, Declaration, Deliverable, Contract, Agreement, Letter |
| Implementing circle | Required for non-system — named circle(s) responsible for execution |
